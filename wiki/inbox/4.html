Closes #3.

What

parse() kept only keys declared on PageFrontmatter and dump() wrote back
only asdict(fm), so every read-modify-write path silently deleted frontmatter a
wiki had added itself. Unknown keys now round-trip through an extra mapping and
are re-emitted after the known fields.

Following the issue's suggested fix

The three implementation gotchas called out in the issue comment are all handled:

  1. extra lands in _FIELDS (it is derived from the dataclass) — parse
    filters on _KNOWN_KEYS = _FIELDS - {"extra"}, so a page with a literal
    extra: key is treated as unknown and round-trips at top level rather than
    being swallowed by the container.
  2. asdict would nest it — dump pops extra and merges it at top level.
    With sort_keys=False the merge order is the emit order, so ordering is
    known-fields-first then unknowns in original order, as the issue asked.
  3. Unknowns bypass _coerce_shapes — we do not own the shape of a field we
    did not define. validate() is untouched and still validates known fields only.

Tests

All four writing call sites from the issue are covered, and each fails against
the pre-fix frontmatter.py:

Test Path Why it matters
test_round_trip_preserves_unknown_fields parse→dump unit level
test_set_preserves_unknown_frontmatter pages.py:138 autowiki set
test_supersede_preserves_unknown_frontmatter_on_both_pages lifecycle.py:90-91 rewrites both pages
test_fix_preserves_unknown_frontmatter_across_every_page lint.py:146 the severe one — rewrites the whole wiki in one command
test_upgrade_preserves_unknown_frontmatter upgrade.py:51 rewrites every page

The set/supersede/lint/upgrade tests arrange by hand-editing the page
file, so they assert the data survives rather than that the carrier field
exists — arranging via fm.extra would have gone red with an AttributeError
instead of on dropped data.

213 passed.

Docs

The issue asked for this to be stated explicitly. README.md now documents that
unknown keys survive every write path, and the SCHEMA.md template tells
maintainers to document any key they add.

Not in scope

The issue's secondary suggestion — omitting unset optional defaults so an edit
produces a small diff — is behavioural and flagged there as its own PR. Not
touched here.
